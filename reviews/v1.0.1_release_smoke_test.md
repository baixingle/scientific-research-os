# Scientific Research OS v1.0.1 Release Smoke Test

## Scope

This is a lightweight repository/specification-level release check for v1.0.1. It does not claim that every host AI, tool connector, instrument, or agent runtime will implement the framework identically.

## 1. Version consistency

**PASS**

- `VERSION` is `1.0.1`.
- `SKILL.md` frontmatter is `version: 1.0.1`.
- `CITATION.cff` identifies version `1.0.1`.
- `README.md` and `RELEASE.md` identify v1.0.1 as the release being published.

## 2. Tool-connected execution boundary

**PASS**

The specification now makes the execution path explicit without claiming that Scientific Research OS itself bundles a universal tool connector or execution engine.

Expected behavior:

```text
scientific question
-> informative next step
-> bounded mission + acceptance criteria
-> available authorized tool/executor performs the work
-> technical acceptance / failure check
-> scientific review and claim boundary
-> state / provenance update
```

The specification also explicitly requires a handoff rather than false execution claims when capability, authorization, safety, or budget is missing.

## 3. Human control and execution truthfulness

**PASS**

- Tool availability is not treated as permission.
- Expensive, irreversible, privacy-sensitive, safety-sensitive, ethically regulated, or strategically consequential actions retain appropriate human approval boundaries.
- Proposed experiments, calculations, searches, analyses, uploads, instrument runs, or other actions must not be represented as completed without execution evidence.

## 4. Backward compatibility with v1.0 scientific core

**PASS**

v1.0.1 does not add a mandatory role, workflow, configuration system, execution product, or domain-specific module.

The existing v1.0 principles remain intact:

- zero-config, natural-language-first entry;
- human researcher as final scientific decision maker;
- competing explanations and information-gain-oriented next steps;
- claim strength proportional to evidence strength;
- bounded execution when useful;
- independent review for consequential conclusions;
- transparent current research state;
- append-oriented provenance and reproducible history;
- domain-neutral scientific-method layer with domain-adaptive execution metadata.

## 5. Cross-domain usability

**PASS**

Synthetic examples are present for:

- wet-lab / experimental research;
- computational / simulation research;
- machine learning / data science.

The execution language remains compatible with theory, literature-driven work, and hybrid research rather than forcing computational metadata onto all domains.

## 6. Release hygiene

**PASS**

- MIT license metadata is present and recognized by GitHub.
- `CITATION.cff` provides version-specific citation metadata.
- `CHANGELOG.md` separates v1.0.1 changes from the immutable v1.0.0 history.
- `RELEASE.md` describes v1.0.1 as a backward-compatible patch and does not rewrite v1.0.0.
- No release step requires modifying the immutable v1.0.0 tag or release.

## Decision

**PASS — v1.0.1 is ready to tag and publish from the current `main` branch.**

The intended release remains a patch-level clarification and usability improvement, not a new architecture generation.
